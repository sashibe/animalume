# 0006. Cocomi 資産（swipe-deck 等）流用判断

## 状況

Animalume は MBTI 診断アプリ、Cocomi は AXP JAPAN 社内の予測市場アプリ。両者の技術スタックには大きな共通点がある：

- Vite + React + TypeScript
- Firebase（Auth + Firestore + Hosting）
- スワイプ UI（swipe-deck コンポーネント）
- 匿名認証フロー
- カテゴリタブ・ボトムナビゲーション

Cocomi で実装済みの資産を Animalume に流用するか、独立実装するかの判断が必要だった。

## 決定

**Cocomi 資産を積極流用する。ただし Animalume リポジトリ内にコピーして独立進化させ、双方向の同期は行わない。**

CLAUDE.md §5.3 に記載のとおり、流用対象は以下：

- `swipe-deck` コンポーネント一式（カードスワイプ UI、アニメーション、状態管理）
- Firestore 接続ラッパー
- 匿名認証フロー
- カテゴリタブ・ボトムナビゲーション基盤

## 理由

### 採用理由

#### MVP-speed-first との直接的整合

CLAUDE.md §4.1 の現フェーズは MVP-speed-first。「動くものを早く出す」が最優先。swipe-deck の再実装は 1〜2 週間規模、流用なら数日。Phase 1 の Implementation Order（CLAUDE.md §8）に対する直接的な高速化要因。

#### 運用検証済み資産の品質優位

Cocomi の swipe-deck は既に実環境で動作した実績がある。ゼロから書き直すよりも、検証済みコードを流用するほうがバグリスクが低い。

#### 技術スタックの完全一致

Vite + React + TS + Firebase という構成は両プロジェクトで一致しているため、流用時のアダプタ層が不要。型定義もそのまま使える。

### 共通モジュール化を採用しない理由

「両プロジェクトで共通の npm パッケージを作る」「monorepo で共有する」といった選択肢は却下した：

#### プロジェクトのフェーズが異なる

- Cocomi: 現状停滞中（メンテナンスモード）
- Animalume: 新規 MVP（活発な変更が予想される）

共通モジュール化すると、Animalume の変更ペースが Cocomi 側の安定性を要求する仕組みと衝突する。

#### 共通リポジトリ管理の運用コスト

ソロ開発（Sori 1 名）にとって、共通モジュールのバージョン管理・破壊的変更の調整・両プロジェクトのテストは過剰な負担。

#### 片方の変更が片方に予期せぬ影響を及ぼすリスク

Animalume で swipe-deck をスワイプ感度・カードサイズ・アニメーションタイミングを変更したい場合、Cocomi 側の挙動を考慮する必要が生じる。これは MVP-speed-first を阻害する。

### 受容するトレードオフ

将来 Cocomi 側で swipe-deck が改善された場合（例：パフォーマンス最適化、新しいジェスチャー対応）、Animalume に自動的に反映されない。手動で cherry-pick する運用となる。

このコストは、ソロ開発の運用負荷バランスで受容する。Phase 6 以降で両プロジェクトの開発体制が変わった場合は、ADR を更新して共通モジュール化を再検討する余地を残す。

## 却下した選択肢

| 選択肢 | 却下理由 |
|---|---|
| 独立実装（流用なし） | MVP 速度を損なう。再実装の意義なし |
| npm パッケージ化して両プロジェクトで共有 | ソロ開発に対して過剰設計。Phase 6 以降に再考の余地 |
| Monorepo（Turborepo 等で統合管理） | 同上、過剰設計 |
| Git submodule で swipe-deck だけ共有 | 運用負荷とリスクのバランスが悪い |

## 流用時の運用ルール

1. Cocomi リポジトリから該当ファイル群をコピーする（git history は引き継がない）
2. Animalume リポジトリにコミットする際、コミットメッセージに「Imported from Cocomi commit <SHA>」を明記
3. Animalume 側で改変を加えた時点で、Cocomi 版とは独立した進化系として扱う
4. 後から Cocomi 側で重要な修正があった場合、手動で cherry-pick または再移植を判断

## 再検討トリガー

以下のいずれかが満たされた時点で本 ADR の見直しを検討する：

- 両プロジェクトの開発体制が変わり、複数人での開発になった（共通モジュール化の運用コスト相対低下）
- swipe-deck の改善が両プロジェクトで頻繁に発生し、手動同期コストが流用コストを上回った
- 第三のプロジェクト（KIREI など）でも swipe-deck が必要になった（共通化のスケール効果が出る）
