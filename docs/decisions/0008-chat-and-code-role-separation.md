# ADR-0008: チャット版 Claude と Claude Code の役割分担

**Status**: Accepted
**Date**: 2026-05-08

---

## Context

Phase 1 系列までは、すべての作業を以下の流れで進めてきた：

```
チャット版 Claude → 指示書作成 → Claude Code が実装
```

Phase 2（シェア体験）の着手時、指示書作成のオーバーヘッドを問題視し、**Claude Code 単独でフェーズ全体を完遂する実験**を行った。引き継ぎ資料 `PHASE2-HANDOFF.md` を Code に直接渡し、議論から実装まで Code 内で完結させる試み。

結果、Phase 2.0 の機能的実装は完成したが、運用上いくつかの構造的問題が観察された。本ADRは、その実証を踏まえて Phase 3 以降の作業フローを定める。

---

## Decision

以下の役割分担を採用する。

- **チャット版 Claude**：思考・判断・対話を担う場。スコープ確定、哲学・トーン議論、バグ報告の原因切り分け、スクショ判断、メタな相談。
- **Claude Code**：実装を担う場。仕様が閉じたタスクの実装、機械的に正しさが判定できる作業（型チェック、ビルド、デプロイ）、リファクタ。
- **基本サイクル**：チャット版でスコープ確定 → Code で実装 → 違和感や判断が混ざる場面でチャット版に戻る。

両者を往復することで、**思考と実装のレイヤーを物理的に分離**する。

---

## Phase 2 で観察された構造的問題

### 1. スコープが沈黙のうちに肥大化する

引き継ぎ資料は OGP 動的生成を Phase 2.1（後回し）と明記していた。にもかかわらず、LINE のシェアカード表示問題に引きずられ、`react-helmet-async` の導入と動的 OGP 注入を Phase 2.0 内で実施した。

Code は実装の手が動くツールであり、**止まるべき分岐点で止まりにくい**。本来必要だったのは「これは Phase 2.1 範囲では。別解として `navigator.share({ files })` で画像ファイル直接シェアに切り替えれば、Phase 2.0 の範囲で解決可能」という対話だったが、レール上で次の手が打たれた。

### 2. 早合点による事実確認の欠落

「ENTJ をシェアしたのに ENHJ が届いた」という曖昧な報告に対し、Code は即座に「画像ファイルに誤植が焼き込まれている」と断定し、PNG 差し替えを指示した。実際には画像は正しく、原因は別（OGP キャッシュか URL 取り違え）の可能性が高かった。

事実確認なしの断定は、開発者が指示を信じた場合に**正しい資産を誤って置き換える事故**を誘発する。チャット版なら「3つの可能性のうちどれか切り分けたい」と止まる場面で、Code は「次の手」を打ちにいく。

### 3. 質的判断が言語化されず通り抜ける

LINE シェアの実装で「LINE が直接起動せず、iOS のシェアシートに引き継がれる」挙動について、開発者は「これはこれでいい」と判断した。判断としては妥当だが、**なぜそれでいいのか**（標準UIの摩擦の少なさ、他メッセンジャー対応の副次効果、quiet luxury との整合）はその場で言語化されず、ADR にも残らなかった。

Code は「これでいい」を「次へ」と読む。判断の根拠を促す対話が起きにくい。

---

## なぜこれは Code の能力の問題ではないか

3つの問題はいずれも、Code の知的能力ではなく**ツール設計の重力**から生じる。ターミナルは「短い指示 → 即実行」に最適化されており、人間側も無意識にその速度に同調する。会話と実装が同じ画面に同居すると、思考の分岐点が失われやすい。

チャット版と Code を物理的に分けることで、思考のレイヤーが分離される。チャット版で判断を煮詰め、Code で実装に集中する。両者の往復が、結果として Animalume の品質基準（quiet luxury、業者っぽさの排除、判断の言語化）を担保する構造になる。

---

## Consequences

**メリット**

- スコープ判断が明示的に行われる
- 質的判断が言語化され、ADR や docs に蓄積される
- バグ報告の原因切り分けが丁寧になる
- スクショ確認・哲学議論など、チャット版の得意領域が活かされる

**トレードオフ**

- 「すぐ済む実装」も一度チャット版を経由すると遅く感じる場面がある
- 単純なバグ修正・リファクタ・型エラー修正は Code 単独で十分。ルールの硬直化は避ける

**運用補助**

- Code に渡す指示書には、必要に応じて以下を明記する：
  - スコープ外の問題は実装せず報告のみ
  - 曖昧な報告には切り分け情報を要求してから着手
  - 「これでいい」と言われた箇所は判断の根拠を一行で提案
- 詳細な運用テクニックが必要になった時点で、別途 `docs/operational-notes/ai-workflow.md` を作成する。

## 運用上の注意点

### interpretations.ts 編集時の _axis パラメータ

`src/features/history/lib/interpretations.ts` の `analyzeAxisChange` 関数は、
第1引数 `axis` を関数本体で使用していない。TypeScript の `noUnusedParameters`
設定により、引数名が `axis` のままだと typecheck で `TS6133` エラーが発生する。

**対策**: 第1引数は必ず `_axis`（アンダースコアプレフィックス）で保持すること。

チャット版から渡される `interpretations.ts` のバージョン（v2, v3 など）は
`axis` のまま記述されていることがある。手動配置時は `_axis` にリネームしてから
typecheck を実行する。

```typescript
// NG
export function analyzeAxisChange(
  axis: Axis,
  previousScore: number,
  currentScore: number,
)

// OK
export function analyzeAxisChange(
  _axis: Axis,
  previousScore: number,
  currentScore: number,
)
```
